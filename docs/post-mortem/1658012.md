# AB#1658012

## Executive Summary

Every Auro component publishes a machine-readable "manifest" that describes it: what it is called, what options it has, and what each option does. Documentation sites, design tools, and AI assistants all read this file. The manifest for `auro-card` already followed the design system's rules, but nothing checked that it stayed that way, so a future change could quietly break it and ship without anyone noticing.

This work adds an automatic quality check to the `auro-card` build. If the manifest breaks the design system's rules, the build now fails instead of publishing a bad file. While in there, we also tightened up the component's descriptions so the manifest, and the documentation generated from it, is accurate and readable by non-engineers.

Ticket: [AB#1658012](https://itsals.visualstudio.com/E_Retain_Content/_workitems/edit/1658012) ("Build Correct CEM - auro-card")

## The Problem

The `custom-elements.json` manifest for `auro-card` passed the design system's strict check with zero findings before this work, but nothing enforced it. A change that broke the manifest would only be discovered later, by a consumer.

Separately, a few descriptions in the manifest were wrong or unhelpful. For example, the `href` description said it "disables the default CTA slot", but the component always renders that slot, and the `relative` description promised a URL re-write feature that the hyperlink used by the card does not act on.

## Root Cause

- `package.json` had `"build": "auro build"` only. `auro build` generates `custom-elements.json` but never validates it against the contract, so no build step could fail on a bad manifest. The repo was also on `@aurodesignsystem/auro-cli` `^3.7.1`, which predates the `cem-check` command.
- `src/auro-card.js`: the class description was a single sentence with no summary or example, slot and part descriptions were terse ("Apply styles to the named cta slot container"), and `variant`, `role`, `href` and `relative` did not describe what they actually do.

## The Fix

- `package.json`: added `"cem:check": "auro cem-check --strict"` and changed `build` to `"auro build && npm run cem:check"`, so a non-zero exit from the check fails the build. Upgraded `@aurodesignsystem/auro-cli` from `^3.7.1` to `^5.1.0` (the ticket asked for 4.0.0 or later).
- `auro-cli` 4.0.0 requires `ADO_TOKEN` to be forwarded by the release-candidate workflow. `.github/workflows/release-candidate.yml` already forwards it (commit `052fa6d`, on the base branch before this work), so no workflow change was needed here.
- `src/auro-card.js`: rewrote the class JSDoc (audience-friendly intro, key capabilities, example, `@summary`), rewrote the slot and `@csspart` descriptions, added `@category` (`ui`, `behavior`) to every property and `@relevantWhen href` to `rel`, `relative` and `target`, and corrected the `register` comment.
- Property descriptions were rewritten to follow the Auro [content guidelines for component documentation](https://github.com/orgs/AlaskaAirlines/discussions/660): `border`, `center`, `href`, `rel`, `relative`, `role`, `target` and `variant`. Each now opens with a verb, gives typical values where it helps, names the native attribute, and is honest about limits (`relative` "does not currently" act). The Key capabilities list names the `variant` values.
- `docs/api.md` and `custom-elements.json` were regenerated by the build.

## Why This Works

- `auro cem-check --strict` treats any finding as a failure, and `&&` in the `build` script propagates that exit code, so CI and local builds both stop on a bad manifest.
- The check validates the manifest after `auro build` has generated it, so it always inspects the file that will actually be published.
- Descriptions were checked against the component's code and styles (`render()`, `setRole()`, `src/styles/style.scss`) rather than the previous wording.

## Outcome

- The `auro-card` build now fails if its manifest breaks the design system's rules. `npm run build` passes and the strict check reports "CEM contract clean — no violations".
- The component's description, option list, and slot and style-part notes are accurate and written in plain language.
- All 7 existing tests pass, and the published package contents include `custom-elements.json`.

## Learnings

- Strict CEM checking costs almost nothing to add when the manifest is already clean, and it turns a silent regression into a build failure. Add it to every component's `build` script.
- Components on older `auro-cli` majors do not have `cem-check`. Upgrade the CLI first, and check that the release-candidate workflow forwards `ADO_TOKEN` (required from 4.0.0).
- Write JSDoc to the Auro [content guidelines](https://github.com/orgs/AlaskaAirlines/discussions/660) from the start. Property descriptions that only repeat the attribute name ("Sets rel attribute on …") are the most common miss; say what the option does and give a typical value.
- Check descriptions against the code. The old `href` description claimed the CTA slot was disabled, but the component always renders it.
- `auro-card` forwards a `relative` attribute to `auro-hyperlink`, but the hyperlink version in use (8.0.3) does not read it. The description now says so. Whether to keep or remove the attribute is a separate decision.
- The commit currently points the `@aurodesignsystem/auro-hyperlink` dev dependency at an unreleased build (`npm:@aurodesignsystem-dev/auro-hyperlink@^0.0.0-pr369.0`). That swap is not part of this ticket and must be restored to a published version (for example `^8.0.3`) before the change merges or ships.
- Pre-existing lint errors (`biome` format on `src/auro-card.js` and `src/hyperlinkVersion.js`, `useNumberNamespace` in `test/auro-card.test.js`) are unrelated to this change and were left alone.
- The build regenerates `README.md` with an invisible-character change and `&#10;` that does not belong to this work, so it was not included.
